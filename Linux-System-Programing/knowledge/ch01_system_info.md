# Chapter 1 - System Information, `/proc`, and Runtime Limits

> Topics: 1.4 `/proc` Filesystem; 1.5 System Limits and Options
> Main sources: TLPI Ch11, Ch12
> Production context: debugging live processes, inspecting kernel state, checking service limits, writing portable Linux/POSIX code, and diagnosing capacity failures in backend or embedded systems.

---

## Problem It Solves

A running Linux system is full of live state:

- processes start and exit;
- file descriptors open and close;
- memory maps change;
- kernel tunables affect behavior;
- runtime limits differ across machines and filesystems.

Hard-coding guesses such as "page size is always 4096" or "filename length is always 255" works until it does not. Production systems fail at the edges: too many open files, a process that exited during inspection, a filesystem with different limits, or a kernel setting that changed behavior.

This topic gives two practical tools:

- `/proc` exposes live kernel and process state through a virtual filesystem;
- `sysconf()`, `pathconf()`, and `fpathconf()` let programs ask for limits instead of guessing.

## Core Vocabulary

| Term | Meaning | Example / note |
|------|---------|----------------|
| `/proc` | Linux virtual filesystem exposing kernel and process information. | Files are generated by the kernel, not stored as normal disk files. |
| procfs | Kernel filesystem implementation behind `/proc`. | Accessed through normal VFS operations. |
| `/proc/<PID>` | Per-process directory for a process ID. | `/proc/1/status` describes PID 1. |
| `/proc/self` | Symlink-like shortcut to the current process's `/proc/<PID>`. | Useful in tools inspecting themselves. |
| `/proc/<PID>/fd` | Directory of symbolic links for open file descriptors. | Great for FD leak debugging. |
| `/proc/<PID>/status` | Human-readable process summary. | Shows IDs, state, memory, signals, groups. |
| `/proc/<PID>/maps` | Memory mapping list for a process. | Useful for memory/debug sessions. |
| `/proc/sys` | Kernel tunables exposed through procfs. | Some writable by privileged users. |
| Kernel tunable | Runtime kernel setting. | `/proc/sys/kernel/pid_max`. |
| `sysconf()` | Runtime query for system/process limits and options. | `_SC_PAGESIZE`, `_SC_OPEN_MAX`. |
| `pathconf()` | Runtime query for file/path-related limits by pathname. | `_PC_NAME_MAX` for a directory. |
| `fpathconf()` | Like `pathconf()`, but uses an open fd. | Good when the file is already open. |
| Indeterminate limit | The implementation cannot report a definite value. | Return `-1` with `errno == 0`. |
| `getconf` | Shell tool for querying POSIX limits/options. | `getconf NAME_MAX .`. |
| `uname()` | API for basic system identity. | Kernel name, release, machine type. |

## Concept Overview

`/proc` makes kernel state look like files:

```text
kernel internal state
    |
    v
procfs
    |
    v
VFS
    |
    v
open/read/write from user space
```

The files are virtual. When you read `/proc/self/status`, the kernel generates text from live process data at that moment.

Limit queries solve a different problem:

```text
program needs a size/limit
    |
    +-- system/process-wide? -> sysconf()
    |
    +-- pathname/filesystem-specific? -> pathconf()
    |
    +-- already have fd? -> fpathconf()
```

Use `/proc` for observation and some Linux-specific tuning. Use POSIX limit APIs when writing code that should adapt across systems or filesystems.

## System Context

### Where `/proc` Fits

`/proc` connects the kernel to user-space observability:

| Tool / use | Typical `/proc` dependency |
|------------|----------------------------|
| `ps`, `top` | process state and statistics |
| `lsof`-style inspection | open file descriptors |
| memory debugging | `/proc/<PID>/maps`, `/proc/<PID>/status` |
| kernel tuning | `/proc/sys/*` |
| service debugging | cwd, exe, fd, environment, limits |

`/proc` is Linux-specific. Many UNIX systems have some form of proc filesystem, but paths and formats are not portable POSIX contracts.

### Where Runtime Limits Fit

Runtime limits sit between portability and resource management:

| Question | API / tool |
|----------|------------|
| How large is a memory page? | `sysconf(_SC_PAGESIZE)` |
| How many FDs can this process open? | `sysconf(_SC_OPEN_MAX)` or resource-limit APIs later |
| How long may a filename be in this directory? | `pathconf(path, _PC_NAME_MAX)` |
| What does the shell see for the same value? | `getconf NAME_MAX .` |

## Architecture

### Practical `/proc` Layout

```text
/proc/
    <PID>/
        status
        cmdline
        environ
        fd/
        maps
        exe
        cwd
        task/
    self/
    meminfo
    cpuinfo
    uptime
    version
    sys/
        kernel/
        fs/
        net/
        vm/
    sysvipc/
```

### Per-Process Files

| Path | What to use it for |
|------|--------------------|
| `/proc/<PID>/status` | IDs, state, memory summary, signal masks, thread count. |
| `/proc/<PID>/cmdline` | Command-line arguments, separated by `\0`. |
| `/proc/<PID>/environ` | Environment variables, separated by `\0`; permissions may restrict access. |
| `/proc/<PID>/fd/` | Open FD targets as symbolic links. |
| `/proc/<PID>/maps` | Virtual memory mappings. |
| `/proc/<PID>/exe` | Executable path. |
| `/proc/<PID>/cwd` | Current working directory. |
| `/proc/<PID>/task/` | Per-thread directories in the process. |

### Limit Query APIs

| API | Scope | Typical constants |
|-----|-------|-------------------|
| `sysconf()` | system/process runtime limits and options | `_SC_ARG_MAX`, `_SC_OPEN_MAX`, `_SC_NGROUPS_MAX`, `_SC_PAGESIZE` |
| `pathconf()` | limits for a pathname / filesystem context | `_PC_NAME_MAX`, `_PC_PATH_MAX`, `_PC_PIPE_BUF` |
| `fpathconf()` | same, but via open fd | `_PC_NAME_MAX`, `_PC_PIPE_BUF` |

## Execution Flow

### Flow 1 - Read Process Info

```text
program opens /proc/<PID>/status
    |
    v
VFS routes to procfs
    |
    v
kernel generates current process data
    |
    v
program reads text bytes
```

### Flow 2 - Inspect Own FDs

```text
program uses /proc/self/fd
    |
    v
kernel resolves self to current PID
    |
    v
fd directory lists open descriptors
    |
    v
readlink() / ls shows targets
```

### Flow 3 - Write a Kernel Tunable

```text
privileged user writes /proc/sys/...
    |
    v
kernel validates value
    |
    +-- invalid -> write fails
    |
    +-- valid -> internal setting changes
```

Many `/proc/sys` changes are immediate but not persistent across reboot unless configured through the system's persistent sysctl mechanism.

### Flow 4 - Query a System Limit

```text
errno = 0
    |
    v
value = sysconf(name)
    |
    +-- value != -1 -> determinate value
    |
    +-- value == -1 && errno == 0 -> indeterminate
    |
    +-- value == -1 && errno != 0 -> error
```

### Flow 5 - `/proc/<PID>` Race

```text
program finds /proc/1234
    |
    v
process 1234 exits
    |
    v
program opens /proc/1234/status
    |
    v
open fails: handle this as normal race
```

Never assume a process still exists just because you saw its directory a moment ago.

## 1.4 `/proc` Filesystem

### What to Remember First

`/proc` is for live inspection. It is intentionally file-like so shell tools and C programs can use ordinary I/O.

Good first-pass files:

| Path | First use |
|------|-----------|
| `/proc/self/status` | See your own process IDs, groups, memory, signal info. |
| `/proc/self/fd` | See your own open file descriptors. |
| `/proc/<PID>/status` | Debug another process. |
| `/proc/<PID>/maps` | See memory mappings. |
| `/proc/sys/kernel/pid_max` | Example of a kernel tunable. |

### Practical Warnings

- `/proc` formats can change across kernel versions; parse by field names, not line numbers.
- `/proc/<PID>` disappears when the process exits.
- Some files are readable only by the process owner or a privileged process.
- Most `/proc/PID` files are read-only.
- Writable `/proc/sys` files should be changed deliberately; they affect kernel behavior.

## 1.5 System Limits and Options

### Why Not Hard-Code?

Limits may vary:

| Variation | Example |
|-----------|---------|
| Across UNIX implementations | different `OPEN_MAX` or supported options |
| Across runtime configuration | resource limits can affect open-file limits |
| Across filesystems | filename length and pipe atomic-write limits |
| Across architecture | page size may differ |

### Common Queries

| Need | Query |
|------|-------|
| Page size | `sysconf(_SC_PAGESIZE)` |
| Max open FDs first-pass | `sysconf(_SC_OPEN_MAX)` |
| Max bytes for `exec()` args/environment | `sysconf(_SC_ARG_MAX)` |
| Max supplementary groups | `sysconf(_SC_NGROUPS_MAX)` |
| Max filename length in a directory | `pathconf(dir, _PC_NAME_MAX)` |
| Max relative path length from a directory | `pathconf(dir, _PC_PATH_MAX)` |

### Handling Indeterminate Results

For `sysconf()`, `pathconf()`, and `fpathconf()`:

```text
return >= 0            -> value known
return -1, errno == 0  -> limit indeterminate
return -1, errno != 0  -> real error
```

This pattern is easy to forget and shows up in interviews because it tests whether you understand API contracts, not just API names.

## Work-Useful Patterns

| Pattern | Why it matters |
|---------|----------------|
| Use `/proc/<PID>/fd` for FD leaks | Shows what a process actually has open. |
| Use `/proc/<PID>/status` for credentials and memory snapshot | Faster than guessing from logs. |
| Parse `/proc` defensively by key names | Kernel versions add/remove fields. |
| Treat `/proc/<PID>` disappearance as normal | Processes are volatile. |
| Use `sysconf()` for process/system runtime limits | Avoids brittle assumptions. |
| Use `pathconf()` for filesystem-dependent limits | Different mounts can have different values. |
| Set `errno = 0` before limit queries | Needed to distinguish error from indeterminate. |
| Use `getconf` to compare shell-visible limits | Quick sanity check without writing code. |

## Advanced / Recognize First

| Topic | Know this much |
|-------|----------------|
| POSIX options | Some features are optional or runtime-checkable; not all UNIX-like systems expose the same APIs. |
| `uname()` | Returns system identity; useful for reporting, not feature detection by itself. |
| `/proc/sysvipc` | Linux exposes System V IPC objects here; useful later in IPC chapters. |
| `/proc/<PID>/task` | Per-thread views live here; important when studying threads. |
| Autoconf-style probing | Build systems may detect limits/features at configure time. |
| `getpagesize()` / `getdtablesize()` | Older alternatives; prefer `sysconf()` first-pass. |

## Example

### Example 1 - Read `/proc/self/status`

```c
#define _POSIX_C_SOURCE 200809L

#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>

int main(void) {
    char buf[512];
    int fd = open("/proc/self/status", O_RDONLY);
    if (fd == -1) {
        perror("open");
        return 1;
    }

    ssize_t n = read(fd, buf, sizeof(buf) - 1);
    if (n == -1) {
        perror("read");
        close(fd);
        return 1;
    }

    buf[n] = '\0';
    printf("%s", buf);

    if (close(fd) == -1) {
        perror("close");
        return 1;
    }

    return 0;
}
```

What it teaches:

- `/proc` is read with normal file I/O;
- the content is generated from live kernel/process state.

### Example 2 - Query runtime system limits

```c
#define _POSIX_C_SOURCE 200809L

#include <errno.h>
#include <stdio.h>
#include <unistd.h>

static void print_sysconf(const char *label, int name) {
    errno = 0;
    long value = sysconf(name);

    if (value != -1) {
        printf("%s = %ld\n", label, value);
    } else if (errno == 0) {
        printf("%s = indeterminate\n", label);
    } else {
        perror(label);
    }
}

int main(void) {
    print_sysconf("_SC_PAGESIZE", _SC_PAGESIZE);
    print_sysconf("_SC_OPEN_MAX", _SC_OPEN_MAX);
    print_sysconf("_SC_ARG_MAX", _SC_ARG_MAX);
    return 0;
}
```

What it teaches:

- runtime limits should be queried;
- `-1` from `sysconf()` needs the `errno` distinction.

### Example 3 - Query a filesystem-related limit

```c
#define _POSIX_C_SOURCE 200809L

#include <errno.h>
#include <stdio.h>
#include <unistd.h>

int main(void) {
    errno = 0;
    long value = pathconf(".", _PC_NAME_MAX);

    if (value != -1) {
        printf("NAME_MAX for current directory = %ld\n", value);
    } else if (errno == 0) {
        printf("NAME_MAX is indeterminate\n");
    } else {
        perror("pathconf");
        return 1;
    }

    return 0;
}
```

What it teaches:

- file-related limits can depend on the filesystem;
- `pathconf()` answers questions tied to a path context.

## Debugging

Useful commands:

```bash
# Inspect process summary
cat /proc/<PID>/status

# Inspect open file descriptors
ls -la /proc/<PID>/fd

# Inspect executable and current working directory
ls -la /proc/<PID>/exe /proc/<PID>/cwd

# Inspect memory mappings
cat /proc/<PID>/maps

# Inspect system-wide state
cat /proc/meminfo
cat /proc/cpuinfo
cat /proc/uptime

# Inspect selected kernel tunables
cat /proc/sys/kernel/pid_max
cat /proc/sys/fs/file-max

# Query limits from shell
getconf ARG_MAX
getconf PAGESIZE
getconf NAME_MAX .
ulimit -n
```

Common bugs:

| Bug | Symptom | Fix / check |
|-----|---------|-------------|
| Treating `/proc` as disk files | Confusion about size, persistence, or contents | Remember procfs is virtual and generated on access. |
| Parsing `/proc` by line number | Breaks across kernel versions | Search for field names. |
| Ignoring `/proc/<PID>` races | Tool fails randomly while scanning processes | Treat missing process files as normal. |
| Hard-coding page size | Memory code fails on unusual systems | Use `sysconf(_SC_PAGESIZE)`. |
| Hard-coding filename/path limits | Fails on different filesystems | Use `pathconf()` / `fpathconf()` or handle errors. |
| Mishandling `-1` from `sysconf()` | Indeterminate value mistaken for fatal error | Set `errno = 0` first. |
| Writing `/proc/sys` casually | System behavior changes unexpectedly | Understand setting and persistence path first. |

## Real-world Usage

| Scenario | Practical design |
|----------|------------------|
| Service has FD leak | Compare `/proc/<PID>/fd` over time and correlate with code paths. |
| Process runs with unexpected user/group | Inspect `Uid:`, `Gid:`, and `Groups:` in `/proc/<PID>/status`. |
| Memory footprint looks high | Start with `/proc/<PID>/status` and `/proc/<PID>/maps`. |
| Embedded system has small resource limits | Query limits at startup and size buffers/resources accordingly. |
| Tool scans all processes | Handle `/proc/<PID>` disappearance without treating it as fatal. |
| Deployment differs across filesystems | Query pathname limits where files will actually be created. |
| Kernel tuning needed | Prefer documented sysctl configuration over ad hoc manual writes. |

## Key Takeaways

- `/proc` exposes live kernel and process state through a virtual filesystem.
- `/proc` files are generated by the kernel, not normal disk-backed content.
- `/proc/<PID>` is per-process and disappears when the process exits.
- `/proc/self` is the current process shortcut.
- `/proc/<PID>/fd` is essential for FD debugging.
- `/proc/<PID>/status` is a quick source for IDs, state, memory, signals, and groups.
- `/proc/sys` exposes kernel tunables; writable entries require care.
- `/proc` formats are Linux-specific and can evolve.
- `sysconf()` queries runtime system/process limits.
- `pathconf()` and `fpathconf()` query file-related limits.
- Some limits can be indeterminate; handle `-1` with `errno = 0`.
- Use `getconf` for quick shell-side checks.
- Production code should query or handle limits instead of assuming them.
